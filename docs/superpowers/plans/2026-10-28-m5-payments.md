# M5 Payments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every booking gets a ledger. Customers pay by bank, JazzCash, Easypaisa or (sandbox) online from their booking link. Managers verify, record and refund. The venue can switch to quick booking (pay and auto-book with a hold).

**Architecture:**
- A new `payments` module owns the ledger maths, the staff and customer payment server code, the provider interface, the sandbox adapter and the payment UI parts.
- The `booking` module keeps statuses, holds and quick booking. It never imports `payments`.
- `payments` imports `booking` through its index. App pages compose the two.
- Every money write is a service-role SQL function that takes the booking row lock. The server checks `can()` first and audits after commit (the M4 pattern in `src/modules/booking/server/staff.ts`).
- The database enforces these rules on its own:
  - the status transition table;
  - `no_overlap` over `confirmed` and `awaiting_advance`;
  - amount limits;
  - provider event idempotency.

**Tech Stack:** Next.js 16.4.2 App Router and Server Actions, React 19.3, Supabase local Postgres, Supabase Storage, Zod 4.6.7, sharp (already installed), Vitest 5, Playwright 1.64. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-28-m5-payments-design.md`. Read it before any task. Its "Owner decisions" section binds exactly.

## Decisions taken in this plan

- **One migration per SQL task:** `20261028000100_payments.sql` (Task 1), `20261028000200_payment_fns.sql` (Task 2), `20261028000300_holds.sql` (Task 3).
- **The range is kept on a `hold_expired` row.** Re-taking it is only a status change back to `confirmed`, so `no_overlap` itself decides. `23P01` then means the slot is taken, and the row goes to `refund_pending`.
- **Quick booking reuses `create_booking_request`.**
  - `create_quick_booking` calls it, which gives the rate limit, customer, reference and token.
  - It then moves the new `requested` row to `awaiting_advance`. The transition `requested → awaiting_advance` is allowed for this purpose only.
  - TS prices each candidate hall, and SQL takes the first free one under the hall lock.
- **Booking range SQL** moves out of `confirm_booking` into an internal helper `booking_during(p_booking uuid) returns tstzrange`, used by confirm and quick booking.
- **Provider selection:**
  - The only provider is `sandbox`.
  - `availableProvider()` returns it only when `PAYMENTS_SANDBOX=1` and `NODE_ENV !== "production"`.
  - `shortcut: one provider per platform; add a moneyRules.gatewayProvider when a second gateway arrives.`
- **Receipt image check** reuses the media module's sniff and header check. Media exports `checkImage(bytes: Buffer, maxBytes: number): Promise<{ ext: "jpg" | "png" | "webp" } | { error: ImageError }>` from its index. It is refactored out of `inspect`, with no behaviour change for media uploads. Receipts are stored as uploaded, not re-encoded.
- **Alerts** are one function `getPaymentAlerts(tenantId)` returning counts and booking ids. They render on the overview page.

## Review Focus

1. **The same webhook twice at the same moment.** Exactly one applies. The other returns `duplicate`, and the ledger has one verified row (db test in Task 2).
2. **A signed webhook whose amount is off by 1 paisa, or whose currency is `USD`.** Rejected as `mismatch`. Nothing is verified or confirmed. The event is still stored, so a replay is a duplicate (db test in Task 2, route test in Task 5).
3. **A customer opens the return URL `/b/<token>?paid=1` without paying.** The page shows "Checking payment". The ledger is unchanged and the booking stays `awaiting_advance` (e2e in Task 6).
4. **A manager lowers a receipt's amount on verify below the advance on an `awaiting_advance` booking.** It stays `awaiting_advance`. A later payment that crosses the advance confirms it (db test in Task 2).
5. **A quick booking against a slot whose only hold expired an hour ago.** The old row becomes `hold_expired`, the new booking holds the slot. Then the old customer's late payment arrives, and the old row goes to `refund_pending` with its payment verified (db test in Task 3).

### Task 2: Ledger SQL functions and settle rule

**Files:**
- Create: `supabase/migrations/20261028000200_payment_fns.sql`
- Test: `tests/db/payments-ledger.test.ts`, `tests/db/payments-provider.test.ts`

**Interfaces:**
- Consumes: Task 1 schema.
- Produces (service role). All raise `P0001` with the message in quotes:
  ```sql
  record_payment(p_booking uuid, p_kind text, p_method text, p_amount int, p_source text, p_note text,
                 p_receipt_path text, p_provider text, p_provider_ref text, p_actor uuid) returns uuid
  verify_payment(p_payment uuid, p_amount int, p_actor uuid) returns void
  reject_payment(p_payment uuid, p_reason text, p_actor uuid) returns void
  set_payment_terms(p_booking uuid, p_advance_due_on date, p_pay_later boolean, p_actor uuid) returns void
  apply_provider_event(p_provider text, p_event_id text, p_provider_ref text, p_status text,
                       p_amount int, p_currency text, p_payload jsonb) returns text  -- 'applied'|'duplicate'|'mismatch'|'unknown'
  ```
  Internal, not granted: `booking_paid(p_booking uuid) returns int` (Σ verified payments − Σ refunds) and `settle_booking(p_booking uuid) returns void`.
- `record_payment` rules:
  - Takes the hall lock when the booking has a hall, then the booking `for update`.
  - Booking status must be one of `confirmed, awaiting_advance, hold_expired, refund_pending`. A refund is also allowed on `cancelled`. Otherwise `'payment_state'`.
  - A payment amount must be 1..(quote total − paid), and a refund 1..paid. Otherwise `'amount_out_of_range'`.
  - Status: `staff` source → `verified` (with `verified_by` and `verified_at`). `customer_receipt` and `provider` → `pending`.
  - For `customer_receipt`: 3 pending receipts on the booking, or 10 receipt rows created in the last hour, raise `'receipt_limit'`.
  - A verified row calls `settle_booking`.
  - A refund that brings paid to 0 on `refund_pending` sets `refunded`. On `cancelled` it clears `refund_due`.
- `verify_payment`:
  - The payment must be `pending` and `customer_receipt`, else `'payment_state'`.
  - `p_amount` must be 1..(total − paid).
  - Sets verified, then settles.
- `reject_payment`: the payment must be `pending`. Needs a reason of 3..300 characters.
- `settle_booking`:
  - `awaiting_advance` and paid ≥ quote advance → `confirmed`.
  - `hold_expired` and paid ≥ advance → try `confirmed`. Catch `23P01` → `refund_pending`.
  - `hold_expired`, paid < advance, and an overlapping `confirmed`/`awaiting_advance` row in the hall → `refund_pending`.
  - Anything else: no change.
- `apply_provider_event`:
  - Inserts into `provider_events` `on conflict do nothing`. No row inserted → `'duplicate'`.
  - Finds the payment by `(provider, provider_ref)`, or returns `'unknown'`.
  - Amount ≠ the payment's, or currency ≠ `tenants.currency`, → `'mismatch'`, and nothing else changes.
  - `paid` → verified (`verified_by` null), then settle. `failed` → `rejected` with reason `'Payment failed'`.
  - Stores `result`, then returns it.
  - Takes the same locks as `record_payment`.
