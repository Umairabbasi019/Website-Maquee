# Decisions

| Date | Decision | Why |
|---|---|---|
| 2026-10-18 | PKR and Asia/Karachi defaults, configurable per tenant | Pakistan market |
| 2026-10-18 | WhatsApp first, email backup | How customers in Pakistan communicate |
| 2026-10-19 | English now, Urdu later via locale layer | Faster launch |
| 2026-10-19 | Photo-based cinematic site now, owner's drone video later | Footage not yet available |
| 2026-10-19 | Super admin creates tenants; no self sign-up | Platform owner sells and onboards each marquee |
| 2026-10-19 | Only the super admin manages everything; other users get role-scoped views | User requirement |
| 2026-10-19 | 1–2 manager logins per venue (default 2) with full venue control | User requirement |
| 2026-10-19 | Manual payments now; online payment auto-books when the provider confirms; bank API later | User requirement; merchant account not ready |
| 2026-10-19 | Multi-tenant with per-tenant config and feature switches | Sell to many marquees and future plans without code |
| 2026-10-19 | All unique customer/owner features and automatic marketing in MVP, shipped by milestone | User requirement |
| 2026-10-19 | Hosting decided before launch; build portable | User chose "decide later" |
| 2026-10-19 | Built for change: feature modules, adapters, config, "where to change what" table | User requirement |
| 2026-10-19 | Public mockup v6 approved section by section | Visual direction locked |
| 2026-10-19 | `references/` media kept out of git (571 MB) | Repo size; product media lives in object storage |
| 2026-10-20 | Staff sign in with email and password in M1; phone OTP later | Works with local Supabase and needs no SMS provider yet |
| 2026-10-20 | Local development runs on Docker (Supabase CLI) | Same database and RLS as production; safe to reset |
| 2026-10-20 | Login limit defaults: 5 logins per venue, 2 of them managers | Matches the 1-2 manager requirement; the super admin can change both per tenant |
| 2026-10-20 | Only the super admin changes owner memberships and grants above role defaults | User decision; stops a manager from raising their own access |
| 2026-10-20 | Tenant login limit, manager limit, currency and time zone are columns on `tenants`, not settings JSON | The database enforces them with a locked trigger, so they must be real columns |
| 2026-10-20 | Platform admin needs MFA (aal2) in the database, not only in the app | A bug in app code cannot give admin rights to a password-only session |
| 2026-10-21 | Session refresh runs in the proxy | Server components cannot write cookies, so expired sessions would otherwise log users out |
| 2026-10-21 | Halls and slots are written with `tenant.settings.edit` | Simple for M1; revisit in M2/M3 when booking rules are built |
| 2026-10-21 | Members of a paused tenant cannot read their tenant row; the server shows a paused notice | The database blocks everything for paused tenants; only the super admin sees them |
| 2026-10-21 | Custom roles are super admin only until M6 | A tenant owner could create roles with "never" keys or extra manager-like roles that skip the manager limit |
| 2026-10-24 | Site content (hero, captions, event text, contact) is a `content` block inside `tenant_settings`, checked by a Zod schema | A new venue needs only data, not code; one place to edit and validate |
| 2026-10-24 | Section styles are CSS Modules ported from the approved mockup, coloured by theme CSS variables | Keeps the approved look; no venue colour or font in code |
| 2026-10-24 | Venue photos go in a public `venue-media` bucket; only the service role writes | Public pages need plain image URLs and a CDN; writes stay closed to browsers |
| 2026-10-24 | Sites stay noindex while content or catalogue is marked sample | Sample copy and prices must not appear in search as the venue's real offer |
| 2026-10-24 | Depth parallax is a progressive layer: desktop, fine pointer, hardware WebGL2 only; the server `<img>` stays as fallback and LCP | Phones and weak devices keep a fast, stable hero; the effect never blocks first paint |
| 2026-10-24 | Responsive images use server-rendered `<img srcset sizes>` with pixel sizes stored in `media_assets.dims` | Replaced client-side size picking; the browser chooses once, with no layout shift or JavaScript needed |
| 2026-10-24 | `content-visibility: auto` only on unpinned sections | Skips off-screen layout work; pinned scroll scenes need real layout |
| 2026-10-24 | `Intl` formatting stays off hydration: prices formatted on the server, `useAfterIdle` for live hours and the date minimum | First-use `Intl` setup cost hundreds of ms on slow phones |
| 2026-10-26 | Date prices may not overlap within one scope (a tenant's all-events rules, or one event type), but an event-specific range may overlap an all-events one; the pricing service (M4) applies the event-specific rule | A database exclusion constraint keeps each scope unambiguous; a venue can still run a general season and a special price for one event type inside it |
| 2026-10-26 | The site draft is one `site_drafts` row per venue holding the whole site as JSON, written only by the server (`save_site_draft()` with an optimistic revision taken from a global sequence) | One shared draft is simple to show, discard and publish; the revision is never reused, so a stale tab cannot publish over a newer draft |
| 2026-10-26 | Published content (events, packages, offers, add-ons, stage themes, `tenant_settings`) changes only through `publish_site()`; a trigger refuses client writes unless `app.publishing` is set. Limit: a session that can run raw SQL as `authenticated` could set it itself (PostgREST cannot); move publish writes into definer functions and drop the client write policies if clients ever get raw SQL | Edits reach the live site only after the draft checks and one audited transaction; also stops a manager from skipping Publish by calling the API |
| 2026-10-26 | `require_publishing()` tests `current_user`, so trusted SECURITY DEFINER code (`create_tenant_from_template`) can write settings | New tenants must be created without a draft |
| 2026-10-26 | Direct saves, with no draft and an audit trigger or audit call: halls (hire price also needs `prices.edit`), slots, date prices (`calendar.manage`), money rules (`tenant.settings.edit`, `settings.money_rules`; `prices.edit` may change only the `showPriceEstimate` switch, see 2026-10-28) | They are not on the page, so there is nothing to preview; the audit rows still show who changed what |
| 2026-10-26 | Publish needs the union of the keys for every item in the draft; an item the viewer lacks the key for blocks Publish and is listed | A manager cannot publish a super-admin change saved by someone else |
| 2026-10-26 | Uploads pass through the Next server (15 MB check, `serverActions.bodySizeLimit` and `proxyClientMaxBodySize` 16 MB), and `sharp` makes the s/m/l sizes. Limit: Vercel caps bodies at 4.5 MB; switch to signed direct uploads to Storage before deploying there | The server must check content and make `dims`; direct upload waits for hosting to be chosen |
| 2026-10-26 | Replacing a photo uploads a new asset (new key) and swaps it into the draft; the old photo stays until unused and deleted. A Storage key is never overwritten, except `depth.png`, whose URL carries `?v=<dims.depthVersion>` | Public images are cached for a year; a new key is the only safe way to change a photo |
| 2026-10-26 | A photo in use (published site or draft) cannot be deleted; alt text is required | Stops broken images on the live site |
| 2026-10-26 | Money inputs are rupees in the browser and integer paisa in the database; one rupee input is capped at 20,000,000 (2e9 paisa, under the 4-byte integer max) | Price columns are `int`; booking totals in M4 must use bigint |
| 2026-10-26 | Client components import a module only through its `client.ts` entry when the module has server-only code in `index.ts` | Keeps `server-only` code out of the browser bundle without a second lint rule per module |
| 2026-10-28 | Request mode: a customer can request any future date; the public site never shows availability, and only staff see booked days | The owner wants an open calendar and customers must never learn that a date is taken; the manager settles each request by phone |
| 2026-10-28 | No holds in request mode. Holds return with quick booking in M5, using `holdHours` | A request blocks nothing, so there is no hold timer and no job runner in M4 |
| 2026-10-28 | Booking status changes only through the service-role SQL functions `confirm_booking`, `decline_booking` and `cancel_booking`, each taking `p_actor`; the server checks `bookings.edit` first | The quote is computed on the server and must be written with the status in one transaction; browsers cannot call these functions, and the history records who acted |
| 2026-10-28 | A confirmed booking is locked and has one quote (version 1). To change it, cancel and take a new request. Decline and cancel reasons are for staff only; the customer sees a fixed "not confirmed" message | Owner decision; keeps the stored price and dates trustworthy and stops reasons leaking to customers |
| 2026-10-28 | `showPriceEstimate` is a manager setting. `prices.edit` may toggle it alone; every other money rule still needs `tenant.settings.edit`. This replaces the money-rules wording of 2026-10-26 | Owner said the estimate is the manager's call; tax, advance and hold hours stay with the settings key |
| 2026-10-28 | Bookings keep name snapshots (`event_type_name`, `package_name`, `addon_names`); their event type and package ids become null when Publish removes the row | Publish must keep working and the booking must keep showing what the customer chose |
| 2026-10-28 | Only a live venue accepts booking requests; a venue in setup or paused answers with the same invalid message | Setup is a preview, so no real request should reach a venue that is not open |
| 2026-10-28 | A request whose date has passed cannot be confirmed (it shows as expired); it can still be declined or cancelled | An expired request must not become a booking for a day that is gone |
| 2026-10-28 | After an override the customer link shows only the final total and the advance, not the calculated lines. Staff see the lines and "Changed from Rs X: reason" | Lines that do not add up to the price would mislead the customer |
| 2026-10-28 | Booking links: a 32-byte token, only its sha256 stored, expiry 60 days after the event date, `Referrer-Policy: no-referrer` on `/book/sent` and `/b/<token>`, and a 404 when the host's venue is not the booking's venue. (`/b/<token>` was later changed to `same-origin`, see the 2026-10-29 line.) The sent page reads the reference from the token, never from the URL | The token is the credential, so it must not leak or work on another venue's host |
| 2026-10-28 | Request rate limit: 5 per hour per phone and per IP bucket (IPv4, or the /64 of an IPv6 address; IPv4-mapped IPv6 counts as its IPv4), plus 30 per hour per venue, kept in `booking_request_hits`. Keys are HMAC-hashed with `BOOKING_HASH_SECRET`, checked once at server start in `src/instrumentation.ts` (skipped during `next build`) | Stops abuse without storing raw phones or IPs; the same message for every date reveals nothing |
| 2026-10-28 | The booking reference is `<PREFIX>-<YYMM>-<NNNN>` with at least four digits: past 9999 in a month it widens to `-10000` instead of failing | A flood of requests must not stop real customers booking for the rest of the month |
| 2026-10-28 | A package is billed for at least its minimum guests (`max(guests, min_guests)` on the package line, labelled "billed for N guests, package minimum"); per-guest add-ons and date prices use the real count. The request is still accepted and the manager can override | Owner call: the site advertises the package "from" its minimum, so the estimate and default quote must not undercut it |
| 2026-10-28 | Known open item: with JavaScript off, a dashboard Server Action that returns an error re-renders into a Next 16.4 InvariantError about cookies in `createServerClient`. Staff dashboard works with JavaScript; the fix is planned in the access module | Found in M4 review; also affects M3 settings forms, so it is not a booking bug |
| 2026-10-29 | `/b/<token>` and the sandbox checkout page use `Referrer-Policy: same-origin` instead of `no-referrer`; `/book/sent` keeps `no-referrer` | With `no-referrer` the browser sends `Origin: null` on a form post and Next rejects the Server Action. `same-origin` still sends nothing to another site or another venue's host |
| 2026-10-28 | Payments owner decision 1: both booking modes exist per venue and a manager or owner switches between them (`instantBooking`). Each booking keeps the status it was made with, so switching never changes old bookings | Manor wants both ways of working |
| 2026-10-28 | Payments owner decision 2: in Manager first mode the date is blocked the moment the manager confirms, before any advance; payment never changes the status in that mode | The manager has already agreed the date by phone |
| 2026-10-28 | Payments owner decision 3: an unpaid advance past its due date only raises a dashboard alert. Nothing is cancelled or released by the system | Many reference customers pay after the event, so late payment is normal |
| 2026-10-28 | Payments owner decision 4: `payments.verify` holders (owner, manager, accounts) record and verify payments; only holders of both `bookings.edit` and `payments.verify` (owner, manager) switch the mode or the online payment switch | Accounts handles money but must not change how the venue takes bookings |
| 2026-10-28 | Payments owner decision 5: a receipt upload alerts the manager and owner on the dashboard (no WhatsApp until M7) | Staff must notice receipts without a message service |
| 2026-10-28 | Payments owner decision 6: refunds are manual. Staff record a refund after paying it outside the system; no money is sent | No gateway does refunds yet |
| 2026-10-28 | Payments owner decision 7: a rejected receipt never cancels the booking. The manager gives a reason, the customer sees it and can upload again; after the event date the owner is also alerted | Cancelling is always the manager's own action |
| 2026-10-28 | Payments owner decision 8: online payment is built now behind a provider interface with a dev-only sandbox, off by default; a real gateway adapter comes later on request | Plugging in a gateway later needs no rework; production cannot turn the sandbox on |
| 2026-10-28 | Payments owner decision 9: cancelling a booking with money paid asks the manager each time to choose "Keep the money" or "Refund due"; refund due shows as an alert until recorded refunds cover the paid amount | Advance can be non-refundable or refundable case by case |
| 2026-10-28 | Quick booking is at the standard package price (a package is required, no override) and needs `advancePercent` above 0; with 0 the switch has no effect. The hall is the first free one in `listHalls` order (name order; there is no `sort_order` column, add one for a multi-hall venue). If none is free the booking becomes a normal request | A customer who pays first needs a fixed price; Manor has one hall |
| 2026-10-28 | Holds have no job runner: an expired hold is flipped to `hold_expired` under the hall lock by the next write that needs the slot, and reads show it as "Hold expired" meanwhile. The M7 job runner will expire holds on time | No scheduler exists before M7; availability is never public, so nothing else reads holds |
| 2026-10-28 | A verified payment on an `awaiting_advance` booking confirms it even after the hold time; on a `hold_expired` booking it re-takes the range under the hall lock (free: `confirmed`; taken: `refund_pending` plus an alert). The payment stays verified either way; with two such bookings the first verified payment wins | Nobody can take the slot without first flipping the hold, and money received must never be lost |
| 2026-10-28 | Receipts: JPEG, PNG or WebP, at most 4 MB, type checked by content, at most 3 pending and 10 uploads per hour per booking, stored in the private `payment-receipts` bucket with no storage policy (the file passes through the Server Action; staff use a 5-minute signed URL) | 4 MB stays under the 4.5 MB serverless body limit; receipt images must never have a public URL |
| 2026-10-28 | Online payments can only be on when the deployment has a provider (`PAYMENTS_SANDBOX=1` and not a production build) and the venue has its `payments` secret saved. Production cannot switch the `gateway` method on until a real adapter exists | Stops a fake gateway taking real customers' money |
| 2026-10-28 | Payment alerts are live queries on the overview, no table and nothing to dismiss; an alert goes away when its cause is fixed | No stale or fake alert states |
| 2026-10-28 | `auditAfterCommit` lives in the access module (`recordAuditAfterCommit`); booking and payments both use it | One copy of the audit-after-commit helper instead of two |
| 2026-10-28 | A paid provider event is always verified, even if a staff payment lowered the balance meanwhile. The balance may then go negative (overpaid); the ledger shows it, `paymentState` reads `Fully paid` at balance <= 0, and the manager refunds by hand | The gateway already took the money; refusing the event would lose the record |
| 2026-10-28 | The receipt storage path is chosen in TypeScript (random UUID) before the insert, so no payment id is needed first; the payment row is made first through `record_payment`, then the file is stored | A refused payment (limits, wrong status) never leaves a file behind |
| 2026-10-28 | The customer link shows the quote for `awaiting_advance`, `confirmed`, `hold_expired` and `refund_pending` | The customer already saw that price, so held and expired bookings read the same |
| 2026-10-28 | `saveMoneyRules` merges the stored rules, so a form save never resets `advanceDueDays` or `paymentAccounts` | A role that cannot see a field does not post it, so its stored value must survive |
| 2026-10-28 | A quick-booking candidate with `advancePaisa` 0 falls back to a request, and both the request and quick-booking quote snapshots are built by one shared function | Otherwise a hold with nothing to pay could never settle, and two copies of the snapshot code could drift |
| 2026-10-28 | Payment state: `Advance paid` only when the advance is above 0 and paid equals it; otherwise money owing after the advance is met reads `Balance due`. The negative balance is kept and the refund-due alert includes overpaid bookings | Overpayment and late money must stay visible to a manager |
| 2026-10-28 | Alert lists are computed in the service-role SQL function `payment_alerts()` returning booking ids (TypeScript keeps the owner/admin gate); staff RPC calls retry once on deadlock `40P01` | No API row cap on long-lived venues; the failed transaction rolled back, so a retry is safe |
| 2026-10-29 | `createPayment` takes a merchant `providerRef` made first by `provider.newRef()`. Online start is `newRef`, then `record_payment` (pending, with the ref), then `createPayment`; if that throws, the pending row stays and the "online payment pending" alert lists it after 1 hour | Standard merchant-reference gateway flow; the payment row exists before the gateway hears of it. This differs from the spec's `PaymentProvider` sketch (noted there) |
| 2026-10-29 | `peekRef` reads the provider reference out of an unverified webhook body, only to find the payment and so the venue whose secret verifies it; the verified event's reference must then equal the peeked one | No tenant is on the webhook URL; the signature is still checked before anything is written |
| 2026-10-29 | The webhook body is capped at 64 KB (413 above), read raw; the cap is flat for every provider | The body is read before it is verified, so it must be bounded; raise or make it per provider if a real gateway sends larger events |
| 2026-10-29 | The sandbox checkout calls `handleWebhook` in-process with a signed body instead of an HTTP self-fetch | Same verify path, no origin or host problems; the route itself is covered by its unit test |
| 2026-10-29 | Receipt "View" is a GET route (`/dashboard/bookings/receipt/[paymentId]`) that redirects to a 5-minute signed URL with `Cache-Control: no-store`, `X-Robots-Tag: noindex` and `Referrer-Policy: no-referrer`; the venue comes from the dashboard session | A plain link opens in a new tab with or without JavaScript, and no signed link is stored on the page |
| 2026-10-29 | `?alert=<name>` on the bookings list is recomputed on the server (holders of `payments.verify` only) rather than passing ids in the URL | A URL must never carry or widen what a user may see |
| 2026-10-29 | `getStatus` is status-only (pending, paid or failed), so the Check status path cannot compare amount and currency. A shortcut comment marks it; widen `getStatus` to return amount and currency when the first real adapter lands | The sandbox is dev-only; the webhook path already checks amount and currency |
| 2026-10-29 | No "receipt sent" flag after upload; the customer's own pending row ("Checking") is the confirmation. "Checking payment" shows only for a pending online row, and the page does not poll the provider on load | No fake sent or paid states; stuck online payments are caught by the alert |
| 2026-10-29 | Payment accounts (bank, JazzCash, Easypaisa) and `advanceDueDays` are set on the money rules form with `tenant.settings.edit` (the super admin, as in JOURNEYS tenant setup). An account with every field blank is removed; a half-filled one is refused. The setup checklist counts saved accounts | Customers send money to these accounts, so a venue role cannot change them by default; the super admin can grant the key to an owner |
| 2026-10-29 | Money verified after a booking moved into `cancelled` or `refunded` (net of refunds since) shows as refund due; `verify_payment` and the webhook still accept it, and a `refunded` booking can take a refund | Gateway money is already taken, so refusing it would only hide it; the alert clears once a refund covers it |
